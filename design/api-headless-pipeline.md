# Headless BEQ filter creation and publishing

**Status:** planning. No code written.

The goal is to run BEQ filter creation and publishing without a GUI, so it
can be driven by an API, a script or an agent. This document defines the
pipeline, records what already exists, and lists what has to be built.

Automated filter design is **assumed to exist** (step 2). It does not; the
assumption is deliberate, so the rest can be planned around it.

```
1. extract audio to mono (optionally decimate to 1kHz)
2. design a filter                            ← assumed solved
3. simulate against the signal, assess headroom
4. iterate until acceptable
5. associate with a TMDB entry → beqcatalogue format
6. add art, build report, publish (commit to a git repo)
```

**Out of scope**, though the same core objects support them: pre-bass-management
per-channel BEQ and channel grouping/linking; export to devices other than the
minidsp 2x4HD; the JRiver crossover designer (`model/jriver/`, which has its
own `AGENTS.md`); presets, chart limits, and the interactive spectrum view.

---

## Headline findings

1. **The publishing format already exists and is already headless.** The
   beqcatalogue contract is a minidsp 2x4HD XML file with a `<beq_metadata>`
   element appended, generated by `HDXmlParser._overwrite`
   (`model/minidsp.py:165`, metadata at `:214`) against the bundled
   `src/main/xml/flat24hd.xml` template. `model/minidsp.py` has no Qt
   dependency worth the name. Step 5's *output* side is essentially done.
2. **Step 5's input side is entirely widget-bound.** TMDB lookup writes its
   results straight into Qt fields (`model/postbuilder.py:216`), and
   `__build_metadata` (`:293`) reads all 24 metadata fields back off those
   fields. There is no metadata object. This is the same shape as blocker B3.
3. **Nothing in this repository publishes anything.** There is no git code,
   no upload, no push. BEQDesigner writes files; a human commits them. Step 6
   is net-new — but it is also the *easiest* new code, and the hard part
   (what the target repo layout is) lives in the beqcatalogue project, not
   here.
4. **The report renders from the screen only because the GUI was already
   showing a preview.** That is an implementation artefact, not a
   requirement — the requirement is a readable image at a specific size and
   layout. So the headless report is a *spec-driven render*, not a port of
   the dialog's layout engine, and the shipped "pixel perfect" mode already
   defines that spec precisely (§6).
5. **Step 1 needs almost nothing.** Running ffmpeg does not involve Qt —
   verified end to end (§1). The only gap is a missing public accessor for the
   built command. B2 downgrades from M to XS.
6. **`beq_gain` has a real bug waiting for an automated designer.** See §3.

## 1. Extract audio to mono

**Exists.** `Executor` (`model/ffmpeg.py:130`) does exactly this case:
`mono_mix=True` applies per-channel gains accounting for the LFE +10 dB
offset and guards against summation clipping; `decimate_audio=True` resamples
to `ANALYSIS_TARGET_FS` (default 1000). Command construction is Qt-free.

**Verified headless.** A 5.1 → mono → 1 kHz extraction runs with no display,
no `QApplication` and no event loop, producing the correct LFE-weighted mono
downmix (`0.309` on the LFE channel against `0.0977` elsewhere — exactly the
+10 dB offset) and a 1 kHz output:

```
ffmpeg -drc_scale "0" -i in.wav -filter_complex
  "[0:a:0]pan=mono|c0=0.0977*c0+0.0977*c1+0.0977*c2+0.3090*c3+0.0977*c4+0.0977*c5[s0];
   [s0]aresample=1000:resampler=soxr[s1]" ...
```

**Qt is not involved in running ffmpeg.** In the whole ~700-line `Executor`
class the only Qt reference is `QThreadPool.globalInstance().start(...)` in
`execute()` (`model/ffmpeg.py:829`) — backgrounding, not execution. The
`-progress udp://` flag that `AudioExtractor` exists to service is **only
added when a `progress_handler` is set** (`:698`), and `FfmpegProgressBridge`
(`:961`), which receives it, is a plain `socketserver` taking a plain
callback with no Qt either.

**Missing:** just a public accessor. `__ffmpeg_cmd` is private, so a headless
caller currently needs `ex._Executor__ffmpeg_cmd.run(...)` via name mangling.
**[B2 — XS]** Add a property and a three-line `run_sync()`; keep `execute()`
as the GUI's backgrounding wrapper over it.

**What is genuinely non-trivial here** is not Qt but operational: this is the
slowest, least reliable step (network I/O, external binary, minutes to
hours), `cancel()` only works before the job starts, and the remux path
builds a list command run through `subprocess.Popen` (`:757`) rather than
ffmpeg-python. In a service this wants to be a job with a progress channel —
and the existing UDP bridge already supports that without modification.

### Loading the result

`AutoWavLoader` (`model/signal.py:1497`) — docstring: *"Loads signals from wav
files without user interaction"* — is already the headless seam.
`auto_load(name_provider, decimate, offset)` produces one
`SingleChannelSignalData` per channel, each owning an empty `CompleteFilter`.
The GUI reaches it from the extract dialog's "Create Signals" button
(`model/extract.py:508`). **Clean; needs only a `Preferences` for
`ANALYSIS_TARGET_FS`.**

**Memory matters here.** `AutoWavLoader.load` reads the *entire* file into RAM
as float64 before preparing channels. A 2-hour mono 48 kHz track is ~2.8 GB —
the source of the 12 GB warning in `docs/ui/load_signal.md`. At 1 kHz it is
~58 MB. This is why decimation matters, and why D1 is a real question.

### Configuration

Stage 0 in all but name. `ANALYSIS_TARGET_FS` sets the fs every signal is
decimated to, which sets the fs every filter is designed at, which sets the
biquad coefficients; `ANALYSIS_RESOLUTION` and the avg/peak windows change the
curves the designer reads. **These are workflow inputs, not preferences**, and
must be supplyable per-request. Blocked by **[B1]**.

## 2. Design a filter — a pluggable boundary

No designer ships with this repo. The contract a designer must satisfy —
exact `DesignRequest`/`DesignResponse` field shapes, units, validation
rules, worked examples — is specified formally in
**[`designer-interface.md`](designer-interface.md)**, v1.0, written to be
implementable without reading this repo at all. That document is the source
of truth for the contract; this section covers only what it means for
*this* repo. `§15` shows the beqanalyser designer's confirmed answers mapped
onto it — the first concrete implementation, not the definition of it.

**Why a separate document, not inline here:** a designer implementation
should not need to depend on this repo — beqanalyser is a separate codebase
with its own dependency set (hdbscan, scipy — no PyQt, no `model.*`) — and a
contract meant to be handed to another team drifts if it's also half-buried
in a planning document. Two documents already caused real drift once in this
project (merged back in the first pass of this plan); the difference this
time is the two documents have different audiences — one is "how beqdesigner
gets built," the other is "what beqanalyser implements" — so
`designer-interface.md` stays the only place the field-level contract is
described, and everything here links to it rather than restating it.

**What this repo does with a valid `DesignResponse`:**

- **Type/budget/shape validation happens at the contract boundary, on
  receipt** — not deferred to XML write. `get_minidsp_filter_code`
  (`model/minidsp.py:242`) and `CatalogueEntry.__convert`
  (`model/catalogue.py:585`) only ever accept
  `PeakingEQ`/`LowShelf`/`HighShelf`, and `§15.3` is why that's not a real
  restriction on the designer: the exact inverse of a matched-alignment
  rolloff already factors into shelves. The existing biquad-budget
  enforcement (`flatten_filters`/`pad_with_passthrough`/`optimise_filters`,
  `TooManyFilters`) covers the budget; no new gate needed there.
- **Converting a valid response into this repo's own types is still new
  work regardless of which designer is plugged in [B3].** Something has to
  turn `BiquadSpec` objects into a `CompleteFilter` (`model/iir.py:1168`) —
  the type everything downstream consumes. Neither existing path is a
  drop-in: `create_shaping_filter`/`create_pass_filter`
  (`model/filter.py:817`/`:855`) reads Qt widgets; `filter_from_json`
  (`model/codec.py:169`) is closer (same project/preset format) but is
  Q-only and unvalidated. `BiquadSpec` → `FilterSpec` → `create_filter()` is
  new code either way.
- **A decline is a distinct outcome the orchestrator must branch on**
  (item 11, §15.4) — not an empty filter list treated as "no filter" by
  convention.

**Pluggability mechanics — how a designer gets selected and invoked**, which
`designer-interface.md §1`/`§7` leave to this side: **start with a single
in-process Python callable** — `Callable[[DesignRequest], DesignResponse]` —
registered by name (a small registry, or Python entry points under a
`beqdesigner.designers` group). Cheapest way to unblock Phase 1, and matches
what beqanalyser's own result already looks like. A subprocess or HTTP
binding is an adapter serialising the same shapes later, not a redesign —
deferred until something actually needs it (**D8**).

## 3. Simulate and assess headroom

**Exists, but not as callable code.** `SignalData.filter_signal()`
(`model/signal.py:379`) already does the simulation headlessly — gain, optional
pre-filter, optional clip, the filter, optional post-filter, optional clip —
and returns a filtered `Signal`.

**Missing:** the measurement. `WaveformModel.__recalc_stats`
(`model/waveform.py:486`) computes peak, RMS, crest factor and headroom in
four lines and pushes each into a spin box. The same headroom line is
duplicated at `model/analysis.py:402` and, in a third variant, at
`model/extract.py:666`. There is no function to call. **[B5 — the whole stats set, not just headroom.]**

**Cost:** trivial. `signal_stats(signal) -> Stats(peak, rms, crest, headroom)`
in a model module, called from all three existing sites.

### The `beq_gain` bug

The published metadata carries `beq_gain`, the attenuation a user must apply
to avoid clipping. It is populated at `model/postbuilder.py:117`:

```python
if not math.isclose(self.__selected_signal.offset, 0.0):
    metadata['beq_gain'] = f'{self.__selected_signal.offset:.1f}'
```

— i.e. **solely from the signal's load-time offset**. `__build_metadata`
returns `beq_gain: None` and relies on `__get_file_name` mutating the dict it
was passed, which is fragile but works today.

`docs/ui/load_signal.md` says the level can be adjusted *either* by a load
offset *or* by a `Gain` filter. There is a `__find_gain(filters)` helper at
`model/postbuilder.py:343` that would extract the latter — **it is dead code,
never called.**

So: **if the automated designer expresses required attenuation as a `Gain`
filter rather than a signal offset, `beq_gain` will be silently absent from
the published entry** — and per `docs/workflow/beq.md` step 7, that value is
the whole point of the headroom check. This needs deciding before the
designer is wired in (Decision D2).

## 4. Iterate until acceptable

**Missing entirely, and it is a design question rather than a coding one.**
Today a human looks at the chart and decides. With an automated designer the
loop needs a termination condition, and the codebase does not contain one.

What the workflow docs imply the criterion is:

- **Headroom** is the only objective gate — `docs/workflow/beq.md` step 7. But
  note the convention: negative headroom is *recorded* as `beq_gain` for the
  user to apply at their volume control, **not** corrected by changing the
  filter. So headroom does not obviously terminate a loop; it terminates it
  trivially, in one pass.
- **"Does it boost real content or just noise?"** (step 6) is the check that
  actually rejects a filter, and it is explicitly a visual judgement over the
  spectrogram with no numeric criterion anywhere in the code.

**Recommendation:** do not build a convergence loop yet. Make step 3 a
measurement that returns `Stats` plus the derived `beq_gain`, and let the
caller decide. If the designer is deterministic, "iterate until ok" collapses
to design once, measure once, record the gain — and the loop is a caller-side
concern, not an API one. Revisit once the designer's actual failure modes are
known.

## 5. TMDB association → beqcatalogue format

Two halves, in very different states.

**Metadata assembly — missing.** `load_tmdb_info` (`model/postbuilder.py:175`)
searches `api.themoviedb.org/3/search/{movie,tv}` by title+year, then fetches
`/3/{movie,tv}/{id}` for poster path, overview, genres, collection, runtime,
certification and alternate title. Every result is written directly to a
widget; `__build_metadata` (`:293`) then reads 24 fields back off widgets, and
`__validate_metadata` (`:348`) validates by setting tick/cross icons and
returning a bool.

Needed: a `BeqMetadata` dataclass, a `tmdb_lookup(title, year, kind) ->
BeqMetadata` that returns it, and validation that returns errors rather than
painting icons. The dialog then becomes a view over the same object.

> **The TMDB API key is hardcoded in source** — `5e23b4412adb55e7cca19cfb9d0196b6`,
> four occurrences in `model/postbuilder.py`. Acceptable in a desktop binary;
> not acceptable in a server, where it becomes a shared credential with no
> rotation path and per-request rate limiting attributable to one key. Must
> become configuration.

**XML generation — exists, headless, and correct.** `generate_avs_post`
(`model/postbuilder.py:86`) loads `flat24hd.xml`, calls
`HDXmlParser(DspType.MINIDSP_TWO_BY_FOUR_HD, False).convert(template, filt,
metadata, pretty=True)`, and writes the result. The metadata serialiser
(`model/minidsp.py:214`) handles scalars, lists of strings (`audioTypes`),
and lists of `{name, id}` dicts (`genres`, `collection`) which become tags
with an `id` attribute.

The AVS forum post text (`build_avs_post`, `:128`) is straightforward BBCode
assembly from the same metadata — trivially portable once `BeqMetadata`
exists.

**Confirming the contract:** BEQDesigner only ever *reads* the catalogue —
`DatabaseDownloader` (`model/catalogue.py:278`) pulls
`beqcatalogue.readthedocs.io/en/latest/database.json`. The `database.json`
that `CatalogueEntry` parses is **generated by the beqcatalogue project from
the committed XML files**, not by this app. So this repo's output contract is
exactly: *an XML file with `beq_metadata`, plus image files, in the right
place in a git repo.* That is a much narrower and more stable target than
"produce a catalogue entry", and it means §6 does not need to understand
`database.json` at all.

## 6. Art, report, publish

Three separable problems.

**Art — mostly exists.** TMDB already returns `poster_path`
(`model/postbuilder.py:238`); `model/report.py:781` downloads an image from a
URL to a temp file. Composing those into "fetch the poster for this TMDB id"
is small. Note TMDB returns a *path fragment*, not a URL — the image base URL
and size must be supplied, and that is currently done by the user pasting a
full URL.

**Report — a spec, not a port.** `SaveReportDialog` (`model/report.py:36`)
composes image + magnitude chart + filter table into a matplotlib figure via
`MagnitudeModel`, with ~20 layout parameters persisted to preferences, and
saves by calling `savefig` on the Qt canvas's figure (`:525`). That
screen-coupling exists because the dialog was already showing the user a
live preview and saving what they could see — it is **not** a requirement.
The requirement is a readable image at a specific size and layout.

That makes the job much smaller, because the shipped "pixel perfect" mode
already *is* the spec, and `docs/ui/report.md` says it is the only layout
that matters (*"All reports shared on avsforum use the Pixel Perfect Image |
Chart layout"*). Read literally, `__save_pixel_perfect` (`:548`) plus
`__concat_images` (`:578`) do this:

1. `savefig` the chart figure — magnitude curves plus the filter table, with
   **no** image embedded — at native DPI.
2. Open the poster with PIL, resize it to the **chart's pixel width**
   preserving aspect (`:599`).
3. Stack vertically, poster on top, and save (`:605`).

So the published report is a vertical concatenation of two images at a common
width. There is nothing screen-dependent about that description, and step 2–3
are already pure PIL — `pillow` is an existing dependency and
`__concat_images`'s only Qt is a confirmation dialog about RGB conversion for
JPEG output.

**What has to be built** is therefore just step 1 headlessly:

- A canvas shim so `MagnitudeModel` can render into a plain
  `Figure` + `FigureCanvasAgg`. It touches only `canvas.figure`,
  `canvas.draw_idle`, `canvas.mpl_connect`/`mpl_disconnect`, `isVisible` and
  `setVisible` — roughly ten lines.
- The filter table, which is plain matplotlib already
  (`__make_table`/`__add_filters_to_table`, `:175`/`:207`) but reads its
  parameters off widgets — the same extraction shape as **B3**.
- A fixed size and DPI supplied as inputs rather than measured from a window.

Keep `SaveReportDialog` for interactive use; it becomes a second caller of
the same renderer.

**Publish — net-new, no existing code, but now fully specified (D3,
resolved by reading `beqcatalogue`'s own ingestion code, not guessing).**
There is no git integration anywhere in this repo; `BEQ_DOWNLOAD_DIR` is
only a download destination despite `docs/ui/preferences.md` calling it
"git repos which store published beq filters".

`beqcatalogue/beqcatalogue/__init__.py`'s `extract_from_repo()` recursively
globs `**/*.xml` under a configured subdirectory of each source repo it
clones — there is no fixed file-naming or directory-layout convention to
satisfy; any nested path works, since every field it needs comes out of the
`<beq_metadata>` block, not the path or filename. `git.py` therefore needs
no beqcatalogue-specific path logic beyond "write the XML somewhere under
the configured subdirectory."

**Images are the one place beqcatalogue does not read the source repo at
all.** `generate_film_content_page()` embeds `meta['spectrumURL']`/
`meta['pvaURL']` directly as markdown image links — those fields must
already be absolute URLs to hosted images by the time the XML is written,
or the entry is skipped entirely ("No charts found"). Per-user decision:
**images go into a second, separate git repo from the XML** (keeps the XML
repo — the one beqcatalogue actually clones and re-clones on every trigger
— small), with `beq_spectrumURL`/`beq_pvaURL` populated from that repo's
GitHub raw-content URL (`raw.githubusercontent.com/<owner>/<images-repo>/
<branch>/<path>`) once the image is committed and pushed. This is the same
shape as the one legacy per-author convention already in beqcatalogue
(Mobe1969's gitlab-raw-URL image links), generalised rather than copied
verbatim.

**Regeneration is push-triggered, not polled or PR-based.** The XML repo
gets a copy of beqcatalogue's `.github/workflows/trigger.yaml`, which fires
a `repository_dispatch` at `3ll3d00d/beqcatalogue` on every push to
`master`/`main` using a `TRIGGER_BEQCATALOGUE` secret; beqcatalogue's own
`update.yaml` catches that, re-clones every *configured* input repo, reruns
`beqcatalogue/__init__.py`, and auto-commits the regenerated
`docs/database.json`/`docs/database.csv`/`docs/*.md` back into itself.
There is no PR step anywhere in this flow — both the XML repo and the
images repo just need a plain commit + push to their default branch.

**What is still a one-time, out-of-band setup, not pipeline code:** which
repos beqcatalogue clones is a hardcoded list (`repo_configs` in
`beqcatalogue/__init__.py`'s `__main__` block, duplicated in
`update_inputs.sh`'s parallel arrays) — adding the new XML repo means
manually adding a tuple there, once, in the beqcatalogue project itself.
Not blocked on anyone external — the same account owns both repos — but
still not something `git.py` does at runtime.

## 9. The API surface

Shape only; signatures illustrative. Three properties of the workflow drive
it: **signals are expensive** (load and analyse once — minutes and GB),
**filters are cheap** (a design iteration is milliseconds at 1 kHz), and
**everything downstream of design is a pure function of (signal, filter)**.
That points at a session-scoped API; a stateless filter-in/filter-out call
would re-analyse the audio every time.

```python
config  = AnalysisConfig(target_fs=1000, resolution=1.0, ...)   # §1
session = Session(config)

# 1 — extract + load
sig   = session.extract(src, audio_stream=0, mono_mix=True, decimate=True,
                        start_ms=None, end_ms=None)      -> SignalRef
sig   = session.load(path, decimate=True, offset=0.0)    -> SignalRef  # or enter here

# 2 — design, via a pluggable designer (§2), or by hand / inspect
result = session.design(sig, designer='beqanalyser.rolloff_v1')  -> DesignOutcome
#   builds DesignRequest from sig (mono_mix + channels), invokes the
#   registered callable, validates the DesignResponse, and converts it —
#   DesignOutcome is Applied(filters, confidence, diagnostics) | Declined(reason)
session.curves(sig, kind='peak'|'avg'|'median')          -> MagnitudeData
session.set_filters(sig, [FilterSpec(type='low_shelf', freq=18, gain=5,
                                     s=2.2, count=5)])    # manual path, same validation
session.curves(sig, kind='avg', filtered=True)           -> MagnitudeData

# 3 — simulate
session.stats(sig)         -> Stats(peak, rms, crest, headroom, fs)
session.fit(sig)           -> FitResult(biquads, budget, optimised)

# 5 — metadata + publishable XML
meta  = session.tmdb(title='...', year=2018, kind='movie') -> BeqMetadata
xml   = session.to_beq_xml(sig, meta)                      -> str

# 6 — art, report, publish
img   = session.report(sig, poster=meta.poster, width=..., dpi=...) -> Path
session.publish(xml, img, meta)
```

Design notes:

- **`FilterSpec` accepts either `q` or `s` for shelves** (§2), plus `count`,
  and reports both back — the difference between an API that matches the
  documented design method and one that fights it.
- **`curves(..., filtered=True)` is the feedback signal** the designer reads.
  It must be cheap; it is called on every iteration.
- **`stats()` returns the simulation fs** alongside the numbers, so a
  published `beq_gain` is never ambiguous about what it measured (D1).
- **`fit()` reports rather than mutates by default**, with opt-in
  optimisation, because `optimise_filters` changes the response and the
  caller is entitled to see that before accepting it.
- **`to_beq_xml()` validates filter types and budget and fails loudly** (§2),
  rather than letting an unpublishable filter reach XML write.
- **`design()` is a thin wrapper around the §2 contract, not a second
  validation path** — `set_filters()` still enforces types/budget/Q
  regardless of whether the caller went through a plugged-in designer or
  built a `FilterSpec` list by hand. Nothing about the pipeline trusts a
  designer more than a human caller.
- **`Declined` is a value, not an exception.** The orchestrator (item 11)
  must handle it as a normal outcome — publish does not run — matching
  §15.4's "nothing downstream should run on a declined title."

## 10. Where the code lives

The plan says what to build but not where, and that matters more than usual
here because the whole point is a boundary Qt cannot cross.

**Recommendation: one new Qt-free package** under `src/main/python/` — say
`pipeline/` — holding the façade plus every piece extracted from a UI class
(`FilterSpec`/`create_filter`, `signal_stats`, `BeqMetadata`/`tmdb_lookup`,
the report renderer, the publisher).

Two rules make it work:

1. **`pipeline/` must never import `qtpy`.** That is the whole contract, and
   it is testable (§11).
2. **Dependencies point inward.** The GUI imports `pipeline`, never the
   reverse. So extraction means *moving* a function into `pipeline/` and
   having the dialog call it — not adding a parallel copy.

Do **not** relocate existing modules in the first pass. `model/iir.py`,
`model/codec.py`, `acoustics/` and most of `model/jriver/` are already
Qt-free and can be imported as-is; moving them is churn that buys nothing
yet. The one that must change is `model/xy.py` (**B1**), because its
import-time `Preferences` would drag desktop settings into the package
through `iir.py`.

`Preferences` is the awkward boundary. `pipeline/` should take a plain
config object (`AnalysisConfig`); a small adapter on the GUI side maps
`QSettings` onto it. That is B1's fix and the API's config story in one.

## 11. Testing

The repo's own precedent is the right model: `model/jriver/` is the most
format-heavy code in the tree and is pinned by round-trip tests
(`test_dsp_roundtrip.py`) that treat the file format as an executable spec.
The publish path deserves the same, and is cheaper to test than it looks.

**1. The publish round trip — highest value, ~15 lines, works today.**
Build a filter set and metadata, write the beqcatalogue XML via
`HDXmlParser`, read it back with `xml_to_filt` (`model/minidsp.py:257`) and
assert the filters and metadata survive. Verified headless against the
current tree using the `docs/workflow/beq.md` Ready Player One values:

```
LowShelf fc=18.00 q=0.7000 gain=4.50 count=5   -> 22.5 dB total
PeakingEQ fc=40.00 q=2.0000 gain=-3.00
6 biquads (budget 10);  beq_metadata: title, year, audioTypes, gain, genres
genres serialised as <genre id="28">Action</genre>
```

Stacked shelf `count` survives intact, which is the fidelity that actually
matters — a lost `count` would silently publish a 4.5 dB filter instead of a
22.5 dB one. **This test is worth writing before any refactoring starts**,
because it pins the output contract while the code around it moves.

**2. The worked example as a spec.** `docs/workflow/beq.md` documents real
filter values and the response they produce. Script it end to end and assert
the documented numbers reproduce. This is the closest thing to an
acceptance test for the pipeline, and it doubles as a check that the docs
stay true.

**3. The Qt boundary.** Assert `pipeline/` imports no `qtpy` (AST scan over
the package), and that a full pipeline run leaves `QApplication.instance()`
as `None`. Cheap, and it is the only thing preventing the boundary eroding
one convenience import at a time.

**4. Report golden image.** Once size and DPI are inputs rather than window
measurements (§6), the render is deterministic and can be compared against a
checked-in reference with a tolerance. Not worth doing before then.

Existing coverage to build on: `test_minidsp.py` already round-trips device
XML against real `MiniDSP-*.xml` fixtures and `expected_output_*.xml`
goldens — the publish test is a natural sibling. The dialogs remain
untested, which is the argument for pushing behaviour down into `pipeline/`
rather than leaving it in a dialog.

## 14. Decisions

**D1 — Headroom at which sample rate?** The common case decimates to 1 kHz, so
simulation measures the peak of a signal with everything above 500 Hz
discarded. For post-BM BEQ that is arguably right — the sub feed is
low-passed anyway — but it is not the peak of the delivered audio. Loading at
native rate instead costs ~2.8 GB for a 2-hour mono 48 kHz track (float64;
this is the source of the 12 GB warning in `docs/ui/load_signal.md`).
*Recommendation: measure on the decimated signal, but make the simulation fs
an explicit field of the result so a published `beq_gain` is never ambiguous
about what it was measured against.*

**D2 — How is required attenuation expressed?** Signal offset (what
`beq_gain` reads today) or a `Gain` filter (what the dead `__find_gain`
anticipated)? An automated designer will pick one and the metadata must
follow. *Recommendation: signal offset, matching current behaviour and the
docs; delete `__find_gain`, and reject a `Gain` filter in the publish
validation so the mismatch fails loudly rather than silently dropping
`beq_gain`.*

**D3 — beqcatalogue repo conventions: RESOLVED.** Answered by reading
`beqcatalogue`'s own ingestion code (`§6`), not by asking the project:
- No fixed directory layout or file naming — `extract_from_repo()`
  recursively globs `**/*.xml`; only the `<beq_metadata>` content matters.
- Two separate git repos, per-user decision: a small XML-only repo
  beqcatalogue clones, and a second repo for report images, referenced from
  the XML via that repo's GitHub raw-content URL (`beq_spectrumURL`/
  `beq_pvaURL` must already be absolute URLs — beqcatalogue never reads an
  image out of the XML repo itself).
- No branch/PR step — a plain commit + push to each repo's default branch;
  regeneration is triggered by a `repository_dispatch` (a copy of
  beqcatalogue's `trigger.yaml` in the XML repo, firing on push).
- One remaining out-of-band step, not pipeline code: getting the new XML
  repo added to beqcatalogue's hardcoded `repo_configs` list — a one-time
  edit to the beqcatalogue project itself (same owner, not externally
  blocked).

**D4 — Report: RESOLVED — required.** The screen-rendering in the current
implementation is an artefact of the GUI showing a preview, not a
requirement; the requirement is a readable image at a specific size and
layout. Item 9 stays in scope but is a spec-driven render rather than a port
(§6). *Follow-on to pin down before phase 3: the exact target size (fixed
output width, or driven by the poster's native width?) and whether the
filter table sits inside the chart axes or below it.*

**D5 — Who runs this?** A local CLI over the user's own files, or a service?
It changes the answer to D1 (memory budget), the TMDB key handling, whether
extraction needs to be a job, and whether the git credentials are the user's
or a bot's. *Recommendation: build phases 1–3 transport-neutral, decide before
phase 4, since publishing is where identity and credentials first matter.*

**D6 — Catalogue as an input.** `CatalogueEntry.iir_filters()`
(`model/catalogue.py:581`) already turns a published BEQ into filters
headlessly. "Fetch a published BEQ and apply it" bypasses steps 1–5 entirely
and is a much smaller job than this pipeline. Worth confirming whether that is
also wanted — it may be the more common use case.

**D7 — Does designer provenance travel past the design step?** The designer's
confirmed return shape (§15.4) carries confidence, `fc`/slope with
uncertainties, and a fit residual alongside the filter, precisely so a
result can be audited before publish. `BeqMetadata` (item 5, §12) and the
report (item 9) were scoped only for TMDB/filter-table data. *Recommendation:
thread the designer's provenance through the pipeline's design-intake step
into the report (so a human reviewing before publish sees confidence/residual
next to the chart) but keep it out of the published XML — the catalogue
format has no field for it and consumers other than this pipeline have no use
for it.*

**D8 — How does a designer implementation bind to the pipeline?** The §2
contract (`DesignRequest`/`DesignResponse`) is plain data; nothing about it
requires the designer to run in the same process, host or language.
*Recommendation: start with a single in-process Python callable, registered
by name, since that's the cheapest path to Phase 1 and matches what
beqanalyser's result already looks like — a function from a signal to a
filter set plus diagnostics. Defer a subprocess or HTTP binding until
cross-repo or cross-language use actually needs it; the schema doesn't change
when the binding does, so nothing is lost by not building it now. Overlaps
D5 (CLI vs service) — resolve together, not separately.*

The designer is being built separately in

Their confirmed answers slot directly into the §2 contract — this is the

| §2 contract | beqanalyser's confirmed answer |
|---|---|
| `DesignRequest.mono_mix` | §15.2 — `mono_mix`, decimated to 1 kHz, primary input |
| `DesignRequest.channels` | §15.2 — used as a diagnostic (LFE-only vs. all-channel rolloff) |
| `DesignResponse.filters` | §15.3 — matched-alignment exact inverse, closed-form as 2–4 low shelves |

### 15.1 Their open question §9 — "what form does a track arrive in?"

This pipeline answers it. Step 1 already produces a decimated mono signal
headlessly, and `AutoWavLoader` gives per-channel signals if the designer
would rather do its own summing. Extraction does not need to be rebuilt.

### 15.2 Signal domain — resolved: (a), plus (d) as a diagnostic

`AUTOMATED_DESIGN` §3.1 asks for the **bass-managed sum**, reasoning that it
"gives the coherence reference more bandwidth than the LFE channel alone,
which is typically lowpassed at 120 Hz". Three things exist here and none is
quite that:

| Option | What it is | Bandwidth |
|---|---|---|
| (a) `Executor(mono_mix=True)` | full-band sum of all channels, LFE at +10 dB | **full** (500 Hz after decimation) |
| (b) `BassManagedSignalData.sum()` (`model/signal.py:507`) | LR4 LPF at `BASS_MANAGEMENT_LPF_FS` (default **80 Hz**) applied per channel, LFE +10 dB, summed, WCS headroom applied | capped at 80 Hz |
| (c) LFE channel alone | as authored | capped ~120 Hz by the source |

**(b) — the literal "bass-managed sum" — has *less* usable bandwidth than the
LFE channel it is meant to improve on**, because the BM crossover sits below
the LFE lowpass. It is the worst of the three for a coherence reference that
needs content above the knee.

(a) is what the current common-case workflow produces, retains the most
bandwidth, and is the closest match to the *intent* of §3.1 even though it is
not what §3.1 names.

**Confirmed by the designer: (a) `mono_mix`, decimated to 1 kHz, as the
primary input.** `AUTOMATED_DESIGN.md` has been corrected. They also want
**(d) per-channel signals as a diagnostic** alongside it — a mastering
rolloff is common to every channel, an LFE-only rolloff is a single-channel
authoring decision, and the sum can't tell those apart. No new extraction
work either way: step 1 (§1) already produces (a), and `AutoWavLoader`
already gives per-channel signals for (d).

The 1 kHz decimation ceiling (500 Hz after decimation) is confirmed load-
bearing on their side too — it's one of two reasons their coherence
reference band has to be fixed rather than tracking the candidate corner
during the `fc` search (their own §7, a real flaw they hadn't spotted
before this exchange).

### 15.3 Output topology — resolved, no format change needed

`AUTOMATED_DESIGN` §5 makes exact inversion the primary output:
**`1/Ĥ · H_protect`**, an inverse high-pass terminated by a protective
high-pass. §15 originally flagged this as unpublishable, since a general
biquad has no representation in `flat24hd.xml`'s three-type PEQ format
(`get_minidsp_filter_code`, `xml_to_filt`, `HTP1Parser` all reject anything
but `PK`/`SL`/`SH`, and the raw `dec`/`hex` fields nothing reads back). That
turned out to be the wrong frame, not a real blocker.

**The exact inverse of a matched-alignment rolloff already is a low-shelf
cascade.** An RBJ low shelf is algebraically a general biquad with a zero at
`f·√A` and a pole at `f/√A`, both at the shelf's Q. Give `H_protect` the same
alignment as the identified `Ĥ` — the designer's choice to make — and
`1/Ĥ · H_protect` factors into `order/2` sections that are each *exactly* a
low shelf: `f = √(fz·fp)`, `gain = 40·log10(fz/fp)`, `q` = the shared Q.
Verified numerically against LR2/LR4/LR8 targets (residual ~1e-3 dB, the rest
being bilinear pre-warp, not error). Where alignments differ or `H_protect`
is lower order, a numerical fit against the exact target closes the gap at
3–4 biquads with <0.1 dB error, including across a 105 dB span.

**So:**

- No schema change, no `dec`/`hex` route, no `HTP1Parser` change — every
  device already gets the identical filter.
- Budget: 2–4 of the 10 biquads. Not close to binding.
- `PeakingEQ`/`LowShelf`/`HighShelf` stays sufficient; the §2 validate-at-
  design-time constraint is real but no longer in tension with the designer.
- This *sharpens* rather than undercuts `AUTOMATED_DESIGN` §6.3: the
  undercorrection hypothesis isn't about authors being limited by their
  tools' filter types (they weren't — the exact answer is shelves too), it's
  about authors placing one shelf by ear where two are fixed by arithmetic.
  A fitting gap, not a tooling one — and testable against the existing
  catalogue with no downstream change required to act on it.

Step 5's *publish* side (§1 of this document) needed nothing. Only the
*input* side changes — see §15.4 for the richer result shape the designer
now returns.

### 15.4 Abstention replaces "iterate until acceptable"

§4 of this document said step 4 has no termination condition. The designer
supplies one, and it is not a loop: `AUTOMATED_DESIGN` §2.5 makes **abstention
the default**, with a graded confidence rather than a yes/no, and §3.6
abstains when the coherent band does not span the knee.

So the pipeline needs a **no-filter path**, not a convergence loop. Confirmed,
and the return shape is richer than a bare filter-or-not: on success, a
`PeakingEQ`/`LowShelf`/`HighShelf` cascade **plus** graded confidence, the
estimated `fc`/slope and their uncertainties, the fit residual against the
exact inverse target, and the implied `mv_adjust` (§15.5) — or a decline with
a reason code. Never a bare filter. Nothing downstream runs on a decline, and
"we correctly concluded nothing was applied" is a first-class outcome, not an
error.

This changes what `set_filters`/the pipeline's design-intake step (§9) has to
hold onto: not just a `list[FilterSpec]`, but that provenance alongside it,
because the designer's own answer is "the estimates ship even on success —
the disagreement report needs them, and a filter without them cannot be
audited." That provenance is worth surfacing at least as far as the report
(a human should be able to see *why* a filter was accepted before it's
published) — flagged as **D7** below rather than assumed away.

Their §2.3 explains why abstention matters at all: the catalogue is 15,208
positives and zero negatives, so a false positive — inventing a rolloff and
boosting 20 dB of nothing — is both the expensive failure and the one the
catalogue cannot detect.

### 15.5 Headroom — output-only confirmed; "same quantity" retracted

`AUTOMATED_DESIGN` §4.2 wants to "report the implied master-volume
compensation", citing the catalogue's `mv_adjust`. An earlier revision of
this section claimed that's the same quantity as `beq_gain` in the publish
metadata (§3 here) — **that was wrong, caught during `designer-interface.md`
review.** They're two different fields via two different code paths:
`beq_gain` (`model/postbuilder.py:117`) comes from a signal's `offset`;
`CatalogueEntry.mv_adjust` (`model/catalogue.py:465`) is parsed from
`vals['mv']`, sourced from beqcatalogue's own `database.json` — external to
this repo, and not confirmed to be derived from `beq_gain` at all. **[B5]**
`signal_stats()` still supplies whatever `beq_gain` needs; D2 still decides
how *that* is carried. What it no longer settles is what the designer's
`mv_adjust_db` (`designer-interface.md §3`) means relative to it — treat
those as two quantities that happen to serve the same purpose until proven
otherwise, not one quantity under two names.

**A genuine bug turned up during the same check**, in this repo's own
`src/test/python/beq_loader.py` (the catalogue test-harness precedent cited
in §11): `CatalogueDecoder.object_hook` reconstructs a `CatalogueEntry` from
the cached `database.bin` by passing the cached `for_search` dict straight
back in as `vals` — but `for_search` writes the key as `mvAdjust`
(`model/catalogue.py:498`) while `CatalogueEntry.__init__` reads `vals['mv']`
(`:465`). Every entry that survives a `database.bin` round-trip silently
gets `mv_adjust = 0.0`, even though the value is present in the cache file
under the other key. Confirmed against the code; not fixed here since
nothing on this pipeline's build path depends on `beq_loader.py` today, but
worth a one-line fix (read the same key you wrote) whenever that harness is
next touched.

Confirmed via §8 of `designer-interface.md`: **output, not input**, this
part unaffected by the correction above. The designer computes the boost it
believes correct from the measured noise ceiling and reports the implied
compensation; it does not accept a headroom target as a constraint on
inversion, so a playback-chain preference can't leak into an
identification-adjacent answer. Anyone wanting to constrain the result uses
the existing "absolute maximum boost" dial downstream, not this channel. No
new work here, but it does mean D2 should be resolved in a way the designer
can consume — i.e. a number on the result object, not a mutation of a
metadata dict — and, per the correction above, that resolving `mv_adjust_db`
into a published `beq_gain` is its own small piece of new work, not a
pass-through.

### 15.6 A free win: this repo can supply their synthetic harness

Their build order puts **"synthetic harness — apply known high-passes to a
known-good track"** first, and says to start there. Everything that needs is
already here and already headless: `ComplexHighPass`
(`model/iir.py:1350`, Butterworth/Linkwitz-Riley/Bessel at arbitrary order)
to generate the ground-truth rolloff, `Signal.sosfilter`
(`model/signal.py:1074`) to apply it, and `Executor` to prepare source
material. Their step 1 needs no new DSP code — only the harness around it.
